# Учёт рабочего времени

Небольшое веб-приложение для учёта рабочего времени сотрудников:

- добавление сотрудников;
- запуск и остановка таймера с описанием задачи (живой счётчик в интерфейсе);
- отчёт за выбранный период: все записи и общее время каждого сотрудника, фильтр по сотруднику;
- данные хранятся в файле SQLite и сохраняются после перезапуска.

Все имена и задачи в примерах и тестах вымышленные.

## Стек

- **Python 3.10+, только стандартная библиотека** — `http.server`, `sqlite3`, `unittest`.
  Ничего не нужно устанавливать через `pip`, приложение запускается одной командой.
- **Интерфейс** — один HTML-файл, ванильный JavaScript и CSS, без сборки и фреймворков.
- **Хранилище** — SQLite (`data/timetracker.db`, создаётся автоматически).

## Запуск

```bash
python run.py
```

Откройте <http://127.0.0.1:8000>. Параметры: `--port 8080`, `--host 0.0.0.0`, `--db путь/к/файлу.db`.

Заполнить базу вымышленными данными за последние три дня (необязательно):

```bash
python seed.py
```

Запуск тестов:

```bash
python -m unittest -v
```

## Структура

```
run.py                 точка входа (аргументы командной строки)
seed.py                демо-данные
tracker/storage.py     бизнес-логика и работа с SQLite
tracker/server.py      HTTP-сервер: JSON API + отдача статики
tracker/static/        интерфейс (index.html, app.js, style.css)
tests/test_storage.py  проверки логики (таймер, отчёт, сохранение)
tests/test_api.py      проверки через настоящий HTTP-сервер
```

Логика полностью отделена от HTTP: `Storage` можно тестировать без сервера, а время
подставляется через параметр `clock`, поэтому тесты не зависят от реальных часов.

## API

| Метод | Путь | Описание |
|---|---|---|
| GET  | `/api/employees` | список сотрудников и их запущенные таймеры |
| POST | `/api/employees` | `{"name": "..."}` — добавить сотрудника |
| POST | `/api/employees/{id}/start` | `{"task": "..."}` — запустить таймер |
| POST | `/api/employees/{id}/stop` | остановить таймер |
| GET  | `/api/report?from=ГГГГ-ММ-ДД&to=ГГГГ-ММ-ДД[&employee_id=N]` | отчёт за период |

Коды ответов: `400` — неверные данные, `404` — сотрудник не найден,
`409` — конфликт состояния (таймер уже запущен / не запущен, дубликат имени).

## Правила учёта

- У сотрудника одновременно может идти **только один таймер**. Повторный «Старт» возвращает
  ошибку 409 с названием текущей задачи, уже идущий таймер не меняется.
- Период отчёта включает обе даты целиком (`to` — до 23:59:59 этого дня).
- Если запись пересекает границу периода (например, работа через полночь), в отчёт
  попадает только та часть времени, что лежит внутри периода.
- Незавершённый таймер считается в отчёте до текущего момента и помечается «идёт сейчас».
- Пустой отчёт — это не ошибка: возвращается пустой список записей, у каждого
  сотрудника 0 секунд, итог 0.

## Проверки (40 тестов)

`python -m unittest -v` покрывает основные сценарии, в том числе:

| Сценарий | Тест |
|---|---|
| Повторный запуск таймера → 409, первый таймер не изменился | `test_repeated_start_is_rejected_and_keeps_first_timer`, `test_repeated_start_is_409` |
| 8 одновременных запросов «Старт» → создаётся ровно одна запись | `test_concurrent_starts_create_only_one_timer` |
| Пустой отчёт (нет записей / нет даже сотрудников) | `test_empty_report`, `test_empty_report_without_employees` |
| Данные и запущенный таймер переживают перезапуск | `test_data_survives_restart`, `test_data_survives_server_restart` |
| Итоги по сотрудникам и фильтр периода | `test_totals_per_employee_and_period_filter` |
| Запись через полночь делится между днями | `test_entry_crossing_midnight_is_split_between_days` |
| Остановка без запуска, двойная остановка | `test_stop_without_running_timer`, `test_double_stop` |
| Пустое имя/задача, дубликат имени (кириллица, разный регистр) | `test_empty_name_rejected`, `test_duplicate_name_rejected_case_insensitive_for_cyrillic` |
| Неверные даты, «с» позже «по», некорректный JSON | `test_invalid_period`, `test_report_validation`, `test_add_employee_validation` |

### Примеры запросов

1. Исходный запрос — текст тестового задания целиком и просьба:
   > «Надо создать, создай, а я сам опубликую в GitHub».
2. > «Сделай без внешних зависимостей, чтобы проверяющий запустил одной командой.
   > Логику отдели от HTTP, чтобы её можно было тестировать без сервера».
3. > «Что будет, если нажать “Старт” два раза подряд или с двух вкладок одновременно?
   > Добавь тест на гонку».
4. > «Как считается запись, которая начата вечером и закончена после полуночи,
   > если в отчёте выбран один день?»

### Ошибки, найденные и исправленные при проверке

1. **Двойной запрос отчёта.** Кнопка «Показать» использовала общий обработчик, который после
   действия перезагружает данные, — а перезагрузка, если отчёт уже открыт, снова запрашивала
   отчёт. Каждый клик отправлял два одинаковых запроса. Исправлено: у формы отчёта свой
   обработчик (`tracker/static/app.js`).
2. **Гонка при повторном запуске таймера.** Проверка «нет ли уже запущенного таймера» через
   `SELECT` перед `INSERT` не спасает от двух одновременных запросов. Добавлен уникальный
   частичный индекс `ON entries(employee_id) WHERE ended_at IS NULL` — второй таймер
   невозможен на уровне БД, а `IntegrityError` превращается в ответ 409. Плюс кнопка
   блокируется на время запроса, чтобы двойной клик не отправлял запрос дважды.
3. **Дубликаты имён на кириллице.** `COLLATE NOCASE` в SQLite сравнивает без учёта регистра
   только латиницу, «Анна» и «АННА» считались бы разными людьми. Уникальность проверяется по
   отдельному полю `name_key = name.casefold()`.
4. **Граница периода.** Наивное условие `started_at BETWEEN from AND to` теряет весь последний
   день (до `to 00:00`) и целиком засчитывает записи, идущие через полночь. Период берётся как
   `[from 00:00; to+1 день 00:00)`, а длительность обрезается по его границам.
5. **Дата «сегодня» в UTC.** `new Date().toISOString().slice(0, 10)` в браузере даёт дату по
   UTC — в Москве до 03:00 «сегодня» оказалось бы вчерашним днём. Используется локальная дата.
6. **XSS.** Имена и задачи вставляются в страницу через `textContent`, а не `innerHTML`;
   задача `<b>xss</b>` отображается как текст (проверено вручную в браузере).
7. **Отрицательная длительность.** Если системные часы перевели назад между стартом и стопом,
   время окончания берётся не раньше времени начала.
8. **Path traversal при отдаче статики.** Сервер отдаёт только файлы из белого списка,
   запрос вида `/../storage.py` возвращает 404 (есть тест).
9. **SQLite и потоки.** `ThreadingHTTPServer` обрабатывает запросы в разных потоках, а одно
   соединение `sqlite3` между потоками делить нельзя — каждая операция открывает своё
   соединение в транзакции.

## Что можно доработать

- редактирование и удаление записей, ручное добавление забытого интервала;
- экспорт отчёта в CSV;
- часовые пояса сотрудников (сейчас границы дней считаются по времени сервера);
- авторизация, если приложение будет доступно не только локально.
